# 学习案例与扩展依据

以下案例来自用户在 2026-11-16 的计算机体系结构学习及随后的复盘。用于说明互动方法，不作为 MIPS 技术规范。使用时无需访问原始聊天，也不要把其中的具体教学模型推广到所有处理器。

## 1. 跳转地址：先区分对象，才能解释位数

用户先说看不懂跳转，再指出“不知道高四位代表什么，左移被吞掉的两位有什么影响”，随后追问“前六位不都是 op 吗”。

仅重讲“跳转会改变执行位置”没有击中问题。关键是区分三种对象：指令的编码、当前指令所在地址、构造出的目标地址；同时区分固定宽度移位与扩宽后补位。

在来源关系清楚之后，用户自行提出“这样不就限制了它能够跳转的范围吗”。这是开始用规则推导后果的证据。

可迁移做法：公式或图中多个对象形状相似时，标明每部分来自哪里、表示什么、流向哪里。优先解决对象身份，再增加细节。

## 2. 资源复用：一个术语可能指向不同的东西

“同一条指令不能重复使用同一个资源”没有被理解。用户想到的是 rs 与 rt 是否指向同一寄存器，解释者想到的是同一个运算部件承担多次运算。

有效转折是具体展示一条 lw 中两项不同的加法：更新顺序指令地址和计算数据访问地址。于是“重复使用”有了可观察的操作含义。

可迁移做法：解释无效时，检查双方是否在谈同一个对象；不要把术语歧义判断成用户缺乏更基础的知识。

## 3. opcode 与 MUX：认真运行用户提出的替代方案

用户设想 opcode 的各位直接控制 MUX，并质疑为什么需要另一层译码。只说现有编码不是这样，能够纠正规则，却不能回答设计问题。

更有效的比较是承认直接控制可以构成一种方案，再检查它需要多少控制位、如何给寄存器编号和立即数留空间，以及现成设计如何用编号生成一组控制信号。若引入相近的真实设计，应说明它处在什么层次，不能把微指令与程序可见指令混同。

可迁移做法：先确认替代方案的目标，再比较约束与成本；不要把“与教材不同”当作不可行的理由。

## 4. 等待稳定与 exit 0：旁路问题补的是主线前提

用户用编程中的退出状态追问，电路如何区分“已经稳定”与“尚未响应”。问题表面超出课件，实际在追问完成判据。

有效解释区分了课件采用的固定时序保证与其他设计可能采用的完成通知，也说明退出成功与操作完成并非完全相同。

可迁移做法：保留类比中有效的对应关系，再指出边界。不要因类比不完全等价而放弃它。

## 5. ALU result：同一根线的含义依赖正在做的任务

用户疑惑为何 ALU 结果接内存 Address，而不是 Write data。原先的解释沿用了算术指令中“结果就是待写回数据”的理解。

用具体 store 展示“地址计算”与“待存数据”两条路径后，用户指出自己忽略了当前指令。这次修正得到一个可复用的方法：先确认当前任务，再判断同一部件及其输出扮演的角色。

可迁移做法：当同一结构服务多个任务时，在例子中固定任务，避免把局部有效的解释推广成恒定职责。

## 如何加入新案例

扩展由用户请求触发。记录足以改变下一次回应方式的内容即可：

- 用户当时试图解释什么，使用了什么假设或类比。
- 哪种回应没有推进理解，卡点后来定位在哪里。
- 哪个具体例子、比较或对象区分带来了变化。
- 有什么可见证据，以及尚不能据此断言什么。
- 方法适用的情形与边界。

优先补充现有案例中的边界或修正；只有机制确实不同，才添加新的案例。避免堆积整段聊天和学科知识摘要。
